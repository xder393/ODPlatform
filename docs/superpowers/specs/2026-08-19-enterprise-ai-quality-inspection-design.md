# 企业 AI 智能质检平台设计

## 1. 背景与目标

ODPlatform 当前提供目标检测的数据准备、训练、评估和推理能力，以及 PySide6 桌面 Demo。该版本缺少面向企业质检业务的身份与权限、实时作业闭环、知识增强助手和生产可观测性。

本项目将其升级为面向**制造业一线质检员**的企业 AI 应用：摄像头实时发现缺陷，质检员在工作台确认或复检，AI 基于质检规范和历史工单给出处置建议，并把全过程记录为可审计的业务链路。作品应同时展示计算机视觉工程和大模型/RAG 应用能力。

首版验收目标：Docker 一键启动后，质检员能接收模拟实时告警、查看带来源引用的 AI 建议并处置工单；管理员能够管理模型、文档、人员和权限，并追溯完整审计记录。

## 2. 范围

### 纳入首版

- Web 质检作业台与管理后台。
- 模拟 RTSP/视频源的实时帧接入、视觉推理、告警和证据图留存。
- 缺陷工单状态流转：`待确认 → 复检中 → 已处置` 或 `误报`。
- 三类角色：质检员、班组长、管理员；权限按组织和产线范围隔离。
- 质检规范 PDF/Word 与历史缺陷工单的解析、切片、索引和 RAG 问答。
- 视觉模型版本管理、操作审计、日志、指标和健康检查。
- 领域逻辑、API、权限隔离、RAG 降级、端到端闭环测试。

### 不纳入首版

- 直接控制真实产线设备；暂停等高风险动作仅模拟并要求授权用户确认。
- 多地域容灾、真实 MES/ERP 双向集成和大规模 Kubernetes 部署。
- 自动训练或自动发布模型；保留版本登记与推理选择接口。

## 3. 架构

首版采用模块化单体，而非过早拆分微服务。前端使用 React，后端使用 FastAPI，现有 `apps/platform` 保持为独立的视觉推理核心。业务模块通过明确的服务接口调用推理核心，禁止推理核心依赖 Web、数据库或身份模型。

```text
React 作业台 / 管理后台
        │ REST + WebSocket
        ▼
FastAPI：认证、RBAC、工单、审计、模型与知识库管理
        ├── AI 编排：视觉推理适配器、RAG 检索、引用与建议生成
        ├── 异步任务：视频帧、文档解析/索引、告警与报表
        └── odp_platform：YOLO 推理、数据质检、训练评估
        │
PostgreSQL / Redis / 对象存储 / 向量索引 / LLM 与模型供应商
```

FastAPI 以业务模块组织：`identity`、`organization`、`inspection`、`cases`、`knowledge`、`models`、`audit`、`ai_orchestration`。每个模块拥有路由、应用服务、领域模型和仓储接口；跨模块只通过应用服务和显式 DTO 交互。

Redis 用于任务队列、缓存和限流。PostgreSQL 存储事务性业务数据。对象存储保存证据图、视频片段与原始文档。向量索引保存经授权的文档和历史工单片段。首版可提供本地实现以支持 Docker 演示，但应用层不绑定具体供应商。

## 4. 领域模型与权限

核心实体：

- `Organization`：租户边界。
- `ProductionLine`、`Camera`：产线和视频源，均归属一个组织。
- `InspectionEvent`：不可变检测事件，记录模型版本、置信度、时间、类别和证据位置。
- `DefectCase`：对一个或多个检测事件的人工处置聚合，维护状态与责任人。
- `Evidence`：证据图或视频片段的元数据及访问策略。
- `KnowledgeDocument`：质检规范或历史工单的原始文件、解析状态、切片和版本。
- `ModelRelease`：可供推理选择的视觉模型版本与指标摘要。
- `AuditLog`：追加式审计条目，记录谁在何时对何个资源做了什么及请求关联 ID。

质检员仅可查看和处置获授权产线的告警及工单；班组长可复核与分配本产线工单；管理员管理组织内用户、角色、产线、模型和知识文档。所有查询与写入在服务层强制组织与产线范围，前端隐藏不构成授权控制。

## 5. 核心业务流

1. 视频接入任务从摄像头或模拟源获取帧，调用视觉推理适配器。
2. 当结果达到策略阈值时，系统写入 `InspectionEvent`、保存证据、创建或关联 `DefectCase`，并通过 WebSocket 推送告警。
3. 质检员确认缺陷、标记复检或请求模拟暂停；每次状态变化校验角色与产线范围并写入审计日志。
4. AI 编排层以缺陷类别、产品批次和工单上下文检索已授权的规范与历史案例；生成答案时输出引用片段、模型/检索元数据与“仅供辅助决策”标识。
5. 人工最终完成处置，系统保留检测结果、AI 建议、人工决定和审计链路，形成可回溯闭环。

## 6. AI 与 RAG 边界

PDF/Word 规范和历史工单分别进入文档处理流水线：提取文本、结构化元数据、分段、向量化并写入索引。检索过滤条件至少包含组织、文档状态、产线或产品适用范围。回答无足够来源时，系统明确返回“未检索到可靠依据”，不编造处置结论。

视觉模型和 LLM 均通过供应商适配器注入。开发与测试环境使用可确定的模拟 LLM；生产部署可切换模型供应商。大模型没有数据库写权限、没有设备控制权限；所有会改变工单状态的操作必须由前端明确请求、后端授权并写审计。

## 7. 非功能要求

- 实时任务、文档解析和报表使用队列，避免阻塞 API 请求。
- 摄像头断流、模型不可用、检索失败与 LLM 失败均写结构化日志并告警；系统降级为人工复检而非中断工单流程。
- 认证使用 JWT；密码使用安全哈希；API 使用 Pydantic 校验、统一错误码、限流和请求 ID。
- 可观测性包括健康检查、结构化日志、帧率、推理延迟、告警量、队列失败率与 RAG 命中率。
- 各服务接口以幂等键处理重复投递；状态更新采用乐观并发或版本号避免并发处置覆盖。

## 8. 测试与验收

- 单元测试：工单状态机、权限策略、检索过滤、引用格式、模型适配器和审计写入。
- 集成测试：认证、组织/产线数据隔离、REST API、异步任务和对象存储接口。
- 端到端测试：模拟视频源触发告警，质检员登录并处置工单，AI 返回可验证的规范引用，管理员查询对应审计记录。
- 可靠性测试：断流、推理超时和 LLM 不可用时均生成可操作的失败状态并支持人工处理。
- 交付测试：全新环境执行 Docker Compose 后，可用预置演示数据完成上述闭环。

## 9. 实施顺序

1. 建立 Web/服务端/共享 Schema 的可运行骨架与 Docker 开发环境。
2. 落地认证、组织、RBAC、审计和数据库迁移。
3. 落地实时检测适配、检测事件、工单状态机和 WebSocket 工作台。
4. 落地文档与历史工单索引、RAG 引用回答和失败降级。
5. 完成管理后台、模型版本、可观测性、自动化测试与演示数据。

此顺序优先交付可演示的质检闭环，再加入知识增强与生产化能力；每一阶段保持可运行、可测试。
