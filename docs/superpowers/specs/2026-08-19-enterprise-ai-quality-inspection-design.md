# 企业 AI 智能质检平台设计

## 1. 背景与目标

ODPlatform 当前提供目标检测的数据准备、训练、评估和推理能力，以及 PySide6 桌面 Demo。该版本缺少面向企业质检业务的身份与权限、实时作业闭环、知识增强助手和生产可观测性。

本项目将其升级为面向**制造业一线质检员**的企业 AI 应用：摄像头实时发现缺陷，质检员在工作台确认或复检，AI 基于质检规范和历史工单给出处置建议，并把全过程记录为可审计的业务链路。作品应同时展示计算机视觉工程和大模型/RAG 应用能力。

首版验收目标：Docker 一键启动后，质检员能接收模拟实时告警、查看带来源引用的 AI 建议并处置工单；管理员能够管理模型、文档、人员和权限，并追溯完整审计记录。

## 2. 范围

### 纳入首版

- Web 质检作业台与管理后台。
- 模拟 RTSP/视频源的实时帧接入、视觉推理、告警和证据图留存。
- 缺陷工单状态流转：`待确认 → 复检中 → 已处置` 或 `误报`。
- 三类角色：质检员、班组长、管理员；权限按组织和产线范围隔离。
- 质检规范 PDF/Word 与历史缺陷工单的解析、切片、索引和 RAG 问答。
- 视觉模型版本管理、操作审计、日志、指标和健康检查。
- 领域逻辑、API、权限隔离、RAG 降级、端到端闭环测试。

### 不纳入首版

- 直接控制真实产线设备；暂停等高风险动作仅模拟并要求授权用户确认。
- 多地域容灾、真实 MES/ERP 双向集成和大规模 Kubernetes 部署。
- 自动训练或自动发布模型；保留版本登记与推理选择接口。

## 3. 架构

首版采用模块化单体，而非过早拆分微服务。前端使用 React，后端使用 FastAPI，现有 `apps/platform` 保持为独立的视觉推理核心。业务模块通过明确的服务接口调用推理核心，禁止推理核心依赖 Web、数据库或身份模型。

```text
React 作业台 / 管理后台
        │ REST + WebSocket
        ▼
FastAPI：认证、RBAC、工单、审计、模型与知识库管理
        ├── AI 编排：视觉推理适配器、RAG 检索、引用与建议生成
        ├── 异步任务：视频帧、文档解析/索引、告警与报表
        └── odp_platform：YOLO 推理、数据质检、训练评估
        │
PostgreSQL / Redis / 对象存储 / 向量索引 / LLM 与模型供应商
```

FastAPI 以业务模块组织：`identity`、`organization`、`inspection`、`cases`、`knowledge`、`models`、`audit`、`ai_orchestration`。每个模块拥有路由、应用服务、领域模型和仓储接口；跨模块只通过应用服务、显式 DTO 或领域事件交互。`ai_orchestration` 仅协调请求，不承载领域规则；工单状态、权限和审计仍分别归 `cases`、`identity` 和 `audit` 所有。

业务模块依赖端口而非基础设施实现：`VisionInferencePort`、`RAGRetrievalPort`、`LLMGenerationPort`、`NotificationPort`、`ObjectStoragePort` 和 `TaskQueuePort`。`odp_platform`、向量数据库、对象存储和模型供应商均实现相应适配器；领域层不得直接导入它们。Redis Stream 是首版跨模块事件与跨实例推送骨干，事件至少包含事件 ID、组织 ID、关联 ID 和幂等键。

Redis 用于任务队列、缓存、限流和 WebSocket 跨实例广播。PostgreSQL 存储事务性业务数据。对象存储保存证据图、视频片段与原始文档。向量索引保存经授权的文档和历史工单片段。首版可提供本地实现以支持 Docker 演示，但应用层不绑定具体供应商。WebSocket 网关维护本实例连接并订阅 Redis Stream，使多实例可以水平扩展。

## 4. 领域模型与权限

核心实体：

- `Organization`：租户边界。
- `ProductionLine`、`Camera`：产线和视频源，均归属一个组织。
- `InspectionEvent`：不可变检测事件，记录模型版本、置信度、时间、类别和证据位置。
- `DefectCase`：对一个或多个检测事件的人工处置聚合，维护状态与责任人。
- `Evidence`：证据图或视频片段的元数据及访问策略。
- `KnowledgeDocument`：质检规范或历史工单的原始文件、解析状态、切片和版本。
- `ModelRelease`：可供推理选择的视觉模型版本与指标摘要。
- `AuditLog`：追加式审计条目，记录谁在何时对何个资源做了什么及请求关联 ID。

质检员仅可查看和处置获授权产线的告警及工单；班组长可复核与分配本产线工单；管理员管理组织内用户、角色、产线、模型和知识文档。权限采用 RBAC 加资源范围策略：角色授予动作，策略如 `defect_case:update:own_line`、`model_release:manage` 和 `report:export` 决定组织、产线和产品类别范围。ORM 仓储基类自动注入 `organization_id` 条件，服务层再次校验资源范围；前端隐藏不构成授权控制。

`AuditLog` 使用仅追加表，应用账号没有更新或删除权限。每条记录携带前一条记录哈希与自身内容哈希，且 HTTP 请求、WebSocket 消息和异步任务共享关联 ID。证据与文档访问使用短期预签名 URL；高风险的模拟暂停动作要求近期二次认证，真实设备控制不在首版范围。

## 5. 核心业务流

1. 视频接入任务从摄像头或模拟源获取帧，生成 `frame_id + model_version` 幂等键后调用视觉推理适配器。队列积压时按背压策略丢弃过期帧并记录 `SKIPPED`，不无限堆积。
2. 当结果达到策略阈值时，系统写入 `InspectionEvent`、保存证据、创建或关联 `DefectCase`，并通过 WebSocket 推送告警。
3. 质检员确认缺陷、标记复检或请求模拟暂停；每次状态变化校验角色与产线范围并写入审计日志。
4. AI 编排层以缺陷类别、产品批次和工单上下文检索已授权的规范与历史案例；生成答案时输出引用片段、模型/检索元数据与“仅供辅助决策”标识。
5. 人工最终完成处置，系统保留检测结果、AI 建议、人工决定和审计链路，形成可回溯闭环。

## 6. AI 与 RAG 边界

PDF/Word 规范和历史工单分别进入文档处理流水线：文件类型与恶意文件扫描、提取文本、结构化元数据、父子切片和重叠窗口分段、向量化并写入索引。每个切片保存文档版本、页码/段落、适用范围和来源定位。文档更新会生成新版本并触发重新索引；旧版本保留并标记为 `SUPERSEDED`。检索使用向量与 BM25 的混合召回，并至少按组织、文档状态、产线或产品适用范围过滤。回答无足够来源时，系统明确返回“未检索到可靠依据”，不编造处置结论。

项目维护带标注查询—文档对的检索评测集，CI 计算 Recall@k、MRR 和 NDCG 并防止索引改动造成回退。开发环境的 `MockLLMAdapter` 基于缺陷类别和已检索引用生成固定模板；Golden Dataset 校验请求、引用与预期输出，避免依赖真实 LLM 的随机性。

视觉模型和 LLM 均通过供应商适配器注入，并使用统一的 `ModelRequest` 与 `ModelResponse` Schema。开发与测试环境使用可确定的模拟 LLM；生产部署可切换模型供应商。每个 `InspectionEvent` 记录模型版本、预处理参数、阈值和输入帧哈希，以保证结果可复现。首版实现模型健康检查与手动切换；A/B 对比与自动故障切换保留为后续能力。大模型没有数据库写权限、没有设备控制权限；所有会改变工单状态的操作必须由前端明确请求、后端授权并写审计。

## 7. 非功能要求

- 实时任务、文档解析和报表使用状态机：`PENDING → RUNNING → SUCCEEDED / FAILED / RETRYING / DEAD_LETTER`。任务以业务幂等键去重，有超时、指数退避、最大重试次数和死信告警。
- 摄像头断流时标记离线、保留最后帧并自动重连；推理超时时标记该帧 `SKIPPED` 并继续后续帧；检索或 LLM 失败时返回“AI 建议不可用，请人工判断”。所有异常写结构化日志并告警，不中断人工工单流程。
- 认证使用 JWT；密码使用安全哈希；API 使用 Pydantic 校验、统一错误码、CORS 白名单、限流和请求 ID。对象存储采用短期预签名 URL，文档上传实施类型校验和恶意文件扫描。
- 可观测性使用 OpenTelemetry 关联 HTTP、WebSocket、异步任务和数据库调用。指标包括帧率、推理延迟、告警量、队列失败率、RAG 命中率、工单闭环时长、误报率、复检通过率、WebSocket 连接数、消息延迟与断连率。
- 各服务接口以幂等键处理重复投递；状态更新采用乐观并发或版本号避免并发处置覆盖。首版性能基线为 3 路模拟摄像头各 5 FPS、20 个并发工作台用户；生产容量由压测数据决定，接口保留批处理与动态批大小扩展点。

## 8. 测试与验收

- 单元测试：工单状态机、权限策略、检索过滤、引用格式、模型适配器、任务状态机和审计哈希写入。
- 集成测试：认证、组织/产线数据隔离、REST API、异步任务、对象存储接口和 OpenAPI 生成的前后端类型契约。
- 端到端测试：录制视频样本与 Mock 推理/LLM 触发确定性告警；质检员登录并处置工单，AI 返回可验证的规范引用，管理员查询对应审计记录。
- 可靠性测试：断流标记离线并自动重连、推理超时跳过帧、LLM 不可用返回人工判断提示、任务超限进入死信队列；首版通过故障注入测试覆盖这些场景，不引入独立混沌工程平台。
- 交付测试：全新环境执行 Docker Compose 后，种子脚本创建 3 个摄像头、10 个缺陷样本、2 份规范文档和演示账户，并能完成上述闭环。

## 9. 实施顺序

1. 建立 Docker 开发环境、最小演示数据和“模拟视频 → 告警 → 确认 → 关闭工单”的垂直闭环。
2. 在闭环上接入认证、组织范围、RBAC、追加式审计和数据库迁移。
3. 接入实时检测适配、任务状态机、背压、WebSocket 广播和证据留存。
4. 接入文档与历史工单版本化索引、混合检索、RAG 引用回答、Golden Dataset 与失败降级。
5. 完成管理后台、模型版本、OpenTelemetry、自动化测试、负载基线和演示脚本。

此顺序优先交付可演示的质检闭环，再加入知识增强与生产化能力；每一阶段保持可运行、可测试，并可独立演示其增量价值。
